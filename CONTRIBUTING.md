# Подготовка новой коллекции клинических случаев

Этот порядок применяется к каждой новой группе случаев по аналогии с `emergency` и `cardiology`. Цель процесса — получить автономную российскую редакцию, редакторские данные, клинический аудит и воспроизводимый runtime. Исходная зарубежная выгрузка, её идентификаторы и служебные поля в этот репозиторий не включаются.

## 1. Определить границы коллекции

1. Выбрать короткое латинское имя `<collection>`, например `neurology`.
2. Составить перечень случаев и убедиться, что каждый случай относится к заявленной группе.
3. Зафиксировать число случаев и ожидаемые диагнозы до начала преобразования.
4. Создать каталог `data/cases/<collection>/` с файлами:
   - `content.json`;
   - `rules.json`;
   - `runtime-config.json`.

Исходные материалы можно использовать как рабочий источник вне этого репозитория. В итоговые файлы нельзя переносить исходные ID, алиасы, комментарии миграции и поля происхождения.

## 2. Отредактировать содержание на русском языке

Для каждого случая:

1. Назначить собственный стабильный ID вида `case.<collection>.0001`.
2. Использовать русские имя и фамилию пациента.
3. Переписать жалобу, обстоятельства обращения, вопросы и ответы естественным русским языком.
4. Проверить согласование рода, возраста, лица, времени и обращения к пациенту.
5. Устранить буквальные кальки, телеграфные ответы, необъяснённые сокращения и противоречия между вопросом и ответом.
6. Привести единицы измерения, названия методов и медицинские термины к употреблению в российской практике.
7. Не ограничиваться переводом: факты случая должны быть внутренне согласованы и позволять однозначно оценивать решения пользователя.

Результат записывается в `content.json`: сведения о пациенте, предъявление, анамнез и результаты исследований. Результаты исследований считаются закрытой частью сценария.

## 3. Выполнить клиническую адаптацию

1. Найти действующие на дату проверки клинические рекомендации Минздрава России по каждому заболеванию.
2. Зафиксировать их название, версию, год, статус и официальный URL в `data/references/clinical-recommendations.json`.
3. Сверить диагноз, критерии тяжести, обязательную первичную оценку, исследования, лечение, маршрутизацию, противопоказания и признаки ухудшения.
4. Исправить зарубежную или устаревшую логику, если она расходится с российскими рекомендациями.
5. Не превращать отсутствие данных в подтверждённый факт. Если решение зависит от неизвестного признака, добавить структурированный факт или условие.
6. Для лекарственного действия обязательно указать препарат или класс, дозу, путь, время, показания, противопоказания и критерий повторной оценки.
7. Для исследования указать срок выполнения, обоснование и помощь, которую его результат не должен задерживать.

В `rules.json` для каждого случая заполняются диагноз, `actionRules`, `studyRules`, `guidelineIds`, `reviewStatus` и `clinicalAuditRef`.

## 4. Разнести правила по классам оценки

Каждое действие и исследование должно попасть ровно в один осмысленный класс:

- `required` — необходимо в начальном состоянии случая;
- `conditional` — необходимо или допустимо только при явном условии;
- `optional` — допустимо, но не является ключевым решением;
- `not-routine` — рутинно не требуется и не приносит баллы;
- `unscorable-as-specified` — формулировка слишком расплывчата для оценки;
- `unsafe-or-delaying` — потенциально вредит или задерживает приоритетную помощь.

Нельзя скрывать клиническое условие только в пояснительном тексте. Для каждого `conditional`-правила создаётся машинное условие в `runtime-config.json`.

## 5. Добавить машинные факты и альтернативы

В `runtime-config.json`:

1. Описать минимальный набор `facts`, необходимый для вычисления условий.
2. Добавить `factNotesRu`, объясняющие принятые для прототипа допущения.
3. Задать `actionConditions` и `studyConditions` для всех условных правил.
4. Использовать только операции DSL, описанные в `docs/SCHEMA.md`.
5. Через `choiceGroups` моделировать взаимозаменяемые стратегии и ограничивать допустимое число выбранных альтернатив.

Свободный текст не должен заменять вычислимую продуктовую логику.

## 6. Обновить общие справочники

### Действия

Новое действие добавляется в `data/catalogs/actions.json`, если подходящего понятия ещё нет. ID должен описывать клинический смысл, а не формулировку конкретного исходного набора.

### Исследования

Новое исследование добавляется в `data/catalogs/studies.json`. Необходимо заполнить:

- собственный стабильный `id`;
- `preferredNameRu`;
- `kind`;
- `externalCodes`;
- `mappingStatus` и пояснение `notesRu`;
- `fsliCode` для лабораторного понятия.

Перед добавлением нужно проверить, не существует ли уже равнозначное понятие. Дублировать ЭКГ, ОАК или другое общее исследование для каждой коллекции нельзя.

## 7. Сопоставить исследования с НМУ

Сопоставление выполняется по актуальной на дату проверки Номенклатуре медицинских услуг. Код нельзя подставлять по памяти или по названию из коммерческого прейскуранта без проверки нормативного источника.

Для каждой связи в `externalCodes` указываются `system: "ru.nmu.804n"`, код, официальное наименование и `relation`:

- `equivalent` — точное соответствие;
- `broader` — позиция НМУ шире локального понятия;
- `component` — один компонент панели или составного исследования;
- `partial` — совпадает только часть протокола или области;
- `related` — связанная, но не эквивалентная услуга.

Правила сопоставления:

1. Панель нельзя искусственно приравнивать к одной услуге, если в НМУ её компоненты представлены отдельно.
2. Варианты, зависящие от доступа, нагрузки, контраста или протокола, должны иметь соответствующий статус и пояснение.
3. `mapped` используется для прямого соответствия; для сложных случаев применяются как минимум `composite`, `approximate`, `protocol-dependent` или другой явно объяснённый статус.
4. До завершения проверки допустим `pending-nmu-review`, но с ним коллекция не считается полностью подготовленной.
5. Корректный код НМУ описывает услугу, но сам по себе не доказывает клиническую уместность исследования.

## 8. Обработать ФСЛИ отдельно

НМУ и ФСЛИ решают разные задачи. Код НМУ нельзя переносить в `fsliCode`.

- Для лабораторного исследования без подтверждённого соответствия записывается `fsliCode: null`. Это означает «ФСЛИ применим, но код пока не установлен».
- Для нелабораторного исследования поле `fsliCode` не добавляется.
- Код ФСЛИ присваивается только по актуальной выгрузке ФР НСИ с фиксацией версии справочника и даты проверки.
- Наличие `null` не мешает исследовательскому runtime, но ограничивает интеграцию структурированных результатов с МИС и ЛИС.

## 9. Подготовить клинический аудит

Создать `docs/audits/<collection>.md`. Для каждого случая аудит должен содержать:

1. якорь, соответствующий `clinicalAuditRef`;
2. использованные рекомендации и дату проверки;
3. оценку исходной логики;
4. внесённые изменения;
5. оставшиеся риски и допущения;
6. пояснение неточных, составных или зависящих от протокола сопоставлений НМУ.

Структурный валидатор не заменяет клинический аудит. До документированной независимой проверки профильным врачом коллекция сохраняет статус `unsafe-until-clinician-approved`.

## 10. Собрать runtime

Runtime генерируется из редакторских данных и вручную не изменяется:

```bash
node scripts/generate-runtime.mjs --collection <collection>
node scripts/generate-runtime.mjs --collection <collection> --check
```

После добавления постоянной коллекции нужно также включить её в команды `build` и `check` файла `package.json` и обновить перечень коллекций в `README.md`.

## 11. Провести контроль качества

Минимальная проверка перед завершением работы:

```bash
npm run build
npm run check
npm run validate
```

Дополнительно проверить вручную:

- одинаковый набор ID случаев во всех трёх редакторских файлах;
- разрешение всех ссылок на действия, исследования, рекомендации и аудит;
- наличие результата у каждого доступного исследования;
- наличие машинного условия у каждого `conditional`-правила;
- отсутствие условия у безусловного правила;
- отсутствие исходных идентификаторов и полей происхождения;
- отсутствие пустых `externalCodes` и необъяснённых `pending-nmu-review`;
- естественность всех вопросов и ответов на русском языке;
- соответствие runtime текущим входным данным;
- отсутствие случайных изменений в других коллекциях.

## 12. Критерии готовности коллекции

Коллекция подготовлена на уровне `unsafe-until-clinician-approved`, если одновременно выполнено следующее:

- все случаи представлены тремя редакторскими файлами и собираются в runtime;
- выполнена русская редактура и устранены внутренние противоречия;
- правила адаптированы по зафиксированным российским клиническим рекомендациям;
- действия и исследования используют общие собственные ID;
- сопоставление с НМУ завершено либо каждое исключение явно документировано;
- состояние ФСЛИ обозначено честно: подтверждённый код или `null`;
- подготовлен построчный клинический аудит;
- `build`, `check` и `validate` завершаются успешно;
- статус клинической безопасности остаётся `unsafe-until-clinician-approved`.

Статус можно повысить только после документированной проверки профильным врачом. Одобрение структуры, кода, перевода или успешное прохождение автоматических проверок клинической приёмкой не является.
